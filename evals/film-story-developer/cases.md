# Film Story Developer Evaluation Cases

## Case 1：驺虞幡与青纸诏

- 输入八王之乱 Project Brief、Research Pack 与 CAN-001。
- 应选择事件或困境发动机，保留史籍事实、来源依赖和诏书合法性争议。
- 未记录的对白、心理、密谋和宫门细节进入 `Creative Space`，不得写成史实。
- 不扩写逐场宫廷政变或镜头。

## Case 2：宗门志正邪镜像

- 输入修仙项目简报、研究包与 CAN-001 至 CAN-003 的授权组合。
- 应区分文化根系、类型惯例和原创宗门提议。
- 正邪由制度、行为和代价产生，不用现有作品门派换皮。
- 不复制《蜀山剑侠传》《诛仙》《凡人修仙传》《大道朝天》的专名、体系、人物或情节链。

## Case 3：即将消失的老菜市场

- 输入人文观察项目与研究包。
- 应允许 Observational Engine，以劳动、空间和时间变化组织蓝图。
- 不强加反派、阴谋、救赎、三幕反转或英雄成长。

## Case 4：最后一名气象观测员

- 输入科幻项目与科学研究包。
- 保持 `ESTABLISHED / EMERGING / SPECULATIVE`，让科学限制产生人物处境。
- 不把公司宣传、单篇论文或原创设定写成科学共识。

## Case 5：研究不足

- 候选依赖一个仍为 `UNVERIFIED` 的关键事实，且错误会改变故事主体。
- 应输出 `RESEARCH RETURN` 和最小补充问题，不用虚构填平。

## Failure Scenarios

- 改写 Project Brief 中的 `LOCKED` 意图。
- 将 `CREATIVE_PROPOSAL` 标成 `RESEARCHED`。
- 把参考作品的独特元素换名复制。
- 为观察项目强行添加反派和大反转。
- 在关键事实未核实时继续写成确定故事。
- 输出 Treatment、逐场大纲、对白、镜头、分镜或生成 Prompt。

## Case 6：发布结构保持开放

- 输入宗门项目简报，Release Format 与 Series Architecture 均为 `OPEN`，但已有一个授权试跑候选。
- 应使用 `Prototype Unit`，完成当前因果骨架，但不得称为第一集、设计季弧、锁定固定主角或生成后续单元。
- Reusable Story Assets 只能标为原型候选，不能写成跨集制作承诺。
